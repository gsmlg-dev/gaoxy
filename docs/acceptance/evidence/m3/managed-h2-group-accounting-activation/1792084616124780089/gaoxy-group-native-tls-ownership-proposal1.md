## Recommendation and rationale

Keep full native TLS connection information on the existing HTTP/2 connection owner, which already retains `state.ssl` and its connection Admission lease. Construct each native H2 Exchange with `ssl:nil`; it no longer retains this duplicated payload in the request pump. Add `Exchange.ssl_data/1`'s native-H2-specific clause, using the existing `Transport.operation(exchange,:ssl_data)`. Add the corresponding operation on the native owner, returning `{:ok,state.ssl}` after the existing call/4 authorization and an authoritative stream.deadline check. Map closed/timeout operation results to nil at the public metadata API, consistent with its existing unavailable-data convention.

This is an explicit producer/API ownership repair, not removing SSL support. In the live authorized stream worker, Exchange.ssl_data and Plug.Conn.get_ssl_data still return the full original stored metadata, including session_data. Nothing is filtered or reconstructed. Peer certificate handling and secure?/peer/sock data remain unchanged. HTTP1 keeps its existing direct Socket.connection_information path. HTTP3 and other transported Exchanges keep the current stored-ssl clause. No process, dependency, global registry, additional authority, cap increase, arbitrary whitelist or accounting-validator side effect is introduced.

The connection owner's existing call/4 requires the real stream ID, exact token and actual GenServer caller PID matching stream.worker. GroupEndpoint and Plug endpoints run in that worker. The returned operation is immediate; Transport.operation preserves its existing finite request deadline/call bound. The new owner check rejects an expired authoritative stream deadline even if a local Exchange is altered to claim more time. After stream deletion or owner death, existing transport rules deny access. Calls from the owner itself would deadlock; current source callsites invoke SSL data only in endpoint/Plug stream context, never the owner. No owner-side invocation is added.

There is a deliberate ownership compatibility boundary: previously a different process with a copied Exchange could read the stored SSL field without owner validation. It will now receive nil through ssl_data, and the raw internal operation returns closed. This follows the existing native transport operation authority; do not describe it as bit-for-bit behavior for unauthorized copied Exchanges or promise cross-process metadata reads. The parent explicitly requested actual stream/token owner handling. Normal live request/Plug semantics preserve the complete data.

## Comparison with retaining SSL in Exchange

A syntactic `{owner,id,token}` check or setting a named projection marker is insufficient provenance: current native_transport? checks scalar shapes, not a live lease, and each original pump still retains the full term. Supporting that alternative would need an authenticated live constructor/lease receipt or metadata identity validation plus a defensible full retained-copy bound before projecting the field. Making the accountant query runtime owners would also break its current pure validation boundary. OTP full metadata does not fit its finite scalar vocabulary. Expanding that vocabulary one atom at a time is incomplete. Native service Config currently permits only provider/certfile/keyfile/alpn/versions, but this still does not turn OTP's complete term into the accountant's existing closed grammar. The owner-only constructor avoids those new proof/control mechanisms and retains the accountant unchanged.

The proposal preserves the already-existing native connection metadata retention; it does not establish a new complete bound for native connection memory or arbitrary OTP option values. Existing connection/Writer reservations stay exactly as configured, as do all group byte/shape caps. An endpoint explicitly requesting SSL data receives a return-value copy under the normal endpoint API; this value is not silently placed back into Exchange or captured by the production group pump.
