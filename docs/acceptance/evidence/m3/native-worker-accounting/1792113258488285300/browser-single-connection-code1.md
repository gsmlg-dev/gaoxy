## Deterministic selection limit

A single owner must irrevocably select the first accepted client socket, open at most one backend socket for it, and reject all others before any backend connect. Do not reselect, reconnect, replay, splice different client streams, or retry a selected failure into PASS. Emit selection identity and backend-connect count1. Bound total accepted/rejected clients and every deadline; excessive connections fail visibly. Ordinary shutdown/close may reject extras, without forced-reset socket options. A race with unread client bytes can still produce an OS TCP reset; do not promise a FIN-only rejection or treat a selected-stream reset as success.

This makes backend multiplicity deterministic. It does not guarantee the selected Chrome socket carries the navigation or remains open: the first may be speculative/abandoned, and an opaque relay cannot distinguish intent. Such a case must fail within the existing finite deadlines. Choosing the first socket with payload instead still cannot prove which TLS connection Chrome will use. The real request capture and all original assertions decide whether a run qualifies. Current redacted evidence proves an additional genuine connection/writer pair (active5); it does not establish why Chrome opened it or why the earlier target writer exited.

## Required byte and lifecycle contract

Use a single nonblocking selector owner with bounded per-direction queues (for example64KiB each), bounded read chunks, disabled read interest at capacity and partial-write offsets. Forward selected bytes unchanged and in order; no application interpretation or synthetic response. Record direction counts and incremental read/written digests, with exact equality at completion and both queues0. Avoid raw state/TLS internals in logs. One selected pair, explicit descriptor ownership and bounded extra-socket handling keep resources finite; no thread/process per unbounded input.

Propagate EOF only after its queued bytes drain, then shutdown the opposite write half; keep the reverse direction alive until its own EOF and drain. TLS close_notify remains opaque data. Do not close the selected backend to make native joins pass. Unexpected selected EOF/reset/write failure before the authorized browser-close phase remains failure. Relay stop must not initiate selected shutdown; first observe normal browser exit and selected bidirectional completion, then stop/join the relay controller/listener. Require no forced cleanup, no remaining descriptors/readers/workers/groups, both EOFs, queues0 and exact byte equality. Preserve actual native connection/writer live/unjoined-before-authorization checks, exact peer_closed/normal DOWN reasons, Session/worker cleanup, Gate exact3 then exact2 then zero, raw upstream HEAD/GET framing and normal Chrome/profile joins.

The prototype needs scoped relay byte-preservation/partial-write/backpressure/half-close and selected-error checks plus real Chrome H2/H1 evidence. ## Public pause comparison

Gaoxy.pause is supported but unsuitable here: Service204-243 first sets Admission mode paused, then asynchronously suspends the listener; result304-311 leaves the Gate paused. Admission rejects new request workers/begin_request outside ready (admission.ex90-91,236-240), and Service cleanup attachment rejects non-ready mode (service.ex109-110). Existing extra connections remain. Pausing after endpoint capture is already too late to prevent the observed extra pair, and can change the request under test.

ThousandIsland.suspend/1 itself is a public listener-only API: its docs240-258 promise existing connections survive while the listening socket closes. It does not remove already accepted extras or atomically choose the first connection. Gaoxy public info exposes listener identity/status, not a supported backend handle for directly bypassing its coordinated pause. A fixture that introspects a private backend handle and changes listener state mid-test adds a race and bypasses Gaoxy lifecycle. Resume on port0 may also change the port. No current public atomic accept-one-and-pause operation exists in these inspected paths; adding one would expand production/API scope.

A relay is therefore the better bounded fixture candidate for deterministic one-backend admission. Chrome navigation success and target persistence remain explicit runtime requirements; do not infer them from the connection cap.
