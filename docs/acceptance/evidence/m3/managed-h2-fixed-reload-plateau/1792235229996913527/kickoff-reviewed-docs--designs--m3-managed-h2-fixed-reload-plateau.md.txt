## Requirement and acceptance boundary

Each profile performs initial activation, two warmup CAS reloads and twenty measured successful CAS reloads without replacing its actual Gaoxy instance, transport owner/epoch or Store PID. Fixed endpoints have no group health probes: each configured resource is exercised by a genuine GET. Group HEAD/selection/accounting qualification is a later independently designed slice.

## Compared approaches

1. **Recommend: three fixed peer epochs per profile, one persistent SUT.** Prepare three independent bounded peers at one common actual authority/port on127.0.0.1/.2/.3. Assign successive configured resources in batches8/8/7. Keep one constant public trust bundle containing all three actual CA DER values for TLS sources. Each old epoch is physically closed/publicly confirmed/joined before its process is stopped and its address rebound. This respects accept8/180s while keeping numeric/source serialization classes constant. It needs a small epoch ledger and fresh-versus-reuse request helper.
2. **One peer with23 fresh resource connections.** Simpler fixture shape, but exceeds its unchanged8-accept cap; reject. Raising the cap or silently reusing a retired resource would erase the intended qualification boundary.

Replacing certificates/trust each epoch changes compact source sizes or requires a new peer certificate-import API. Neither is necessary for this bounded slice; reject.

There is no need to split the recommended eight profiles further before execution.
