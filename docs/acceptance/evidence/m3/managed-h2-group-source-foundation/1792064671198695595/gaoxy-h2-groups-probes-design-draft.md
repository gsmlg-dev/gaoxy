## Recommended approach and alternatives

Extend the existing group owner, resource sidecar, Session and Probe with an explicit managed-H2 execution profile. The same group health/selection ledger and managed transport owner continue to own mutable state. Add a bounded origin-neutral request source before selection, then prepare the fixed H2 envelope for exactly the selected member. Admission knows the execution profile before allocating the cleanup hold.

A guard-only change is rejected: Options currently rejects non-H1 members, HTTP.selected_client(group) chooses HTTPFetchClient, preselection request shape is H1, member identity validation hardcodes H1, probes always open HTTPFetchClient, and probe bytes use the H1 formula. Such a change would select an incorrect client or underreserve before Fetch.

Allowing arbitrary mixed H1/H2 groups would require a common preselection reservation, response callback dispatch and failure model for multiple clients. It adds no requirement needed by this bounded successor. Creating a second group owner would duplicate proven health, retirement and selection machinery. Both alternatives are larger than extending the present H2-family profile.

## D1. Options, handles and resource identity

`UpstreamGroups.Options.compile/1` accepts the existing H1 family or the H2 family, rejects mixing the two, and rejects HTTP/3. Each H2 member must have a valid exact four-field managed transport handle and a coherent HTTP config/client. Preserve each member's `upstream_protocol` when recompiling an Options struct; the present struct conversion drops it. Raw and compiled forms must round-trip identically. Preserve existing limits: 1..32 members, unique bounded IDs, origin URL at most 8192 bytes for groups, complete input at most 1048576 serialized bytes, finite endpoint/member limits and current health bounds. Do not broaden fixed-envelope or trust limits.

Keep existing dedicated H1 six-field and managed H1 seven-field handles unchanged. An H2 handle has exactly the existing managed seven fields plus `execution_profile: :managed_h2`. Its `transports` sidecar is unique in first-occurrence order and contains 1..32 exact handles. Resources.validate still caps the flattened `[group | transports]` manifest at 64 handles and 65536 serialized bytes. Validate the new eight-field form explicitly; reject unknown marker values and extra fields. The owner stores and matches the complete handle, including the marker and transport order. A shape-valid fabricated/downgraded handle is never authority: owner record matching and resource pin admission must reject it.

Preparation remains in the facade/preparer. Validate every distinct `{transport, origin, upstream_protocol}` identity against the same instance and absolute deadline before pinning. The protocol must participate in deduplication so reuse of one transport with conflicting declarations is not hidden. Acquire transport preparation pins, then prepare the group. Rollback releases only this attempt's pins and group operation; never retire a shared transport. The embedding must acquire a baseline for the complete flattened resources before releasing preparation pins. Owners must not synchronously call each other.

`GroupEndpoint.init/1` and `resources/1` stay pure. HTTP.selected_client chooses ManagedH2Client for the exact H2 marker before its existing generic group clause. This is classification, not authorization; checkout still authenticates the owner record and selected member. Add GroupEndpoint.generation_validate/1: genuine H2 handles return `{:error, :unsupported_generation_endpoint}`; genuine H1 handles retain existing support. Test Generation.prepare/load rejection before resource pin/publication/listener changes. This slice does not add H2 Generation support.

## D2. Admission and selected-member requests

Before starting a Session, normalize H2 group input to a closed six-key source: `{target, method, fields, body_mode, request_limits, max_upload_bytes}`. Here braces name map keys. `target` is an origin-form binary, including a present empty query; derive it from absolute form only after the same bounded source preflight used for fixed H2. Its logical and backing sizes are at most 65536. Fields have the existing finite count/byte/backing checks; method, body and trailer limits keep the fixed contract. Copy retained binaries only after preflight. The source is compact and origin-neutral; it contains no arbitrary member URI or client policy.

Admission uses handle.max_url_bytes plus target bytes and rejects values over the existing 65536 URL ceiling before Session creation/cleanup attachment. It reserves the new complete H2 group amount described in D4. Reuse the existing delegated pin handoff; no extra group selection or origin lookup occurs in the pump.

Session performs one group checkout, stores the group token, validates/pins/checks out only the selected member transport, and uses that member's actual protocol. Assert the selected config belongs to the handle's H2 profile before opening. Assemble `url = selected_root_origin <> target` and feed the existing ManagedH2Envelope.prepare/2 and ManagedH2Client.open/1. This retains fixed H2 pseudoheader, effective field, upload, response and metadata checks. Preserve raw escapes and present empty query. No alternate member is selected after any denial or upstream failure; no replay occurs.

Bind the same original public RequestCompletion to the transport token, then to the group selection, before notifying ready or permitting upload. Retain independent outer resource pins, Session transport pins/token, group token and Service cleanup hold. Cleanup order remains original completion confirmation, transport finish/pins, group finish with outcome, Service cleanup release. An unconfirmed completion keeps both ledgers/reservations and fail-closed state. Local validation, capacity, pin and checkout denials are neutral for passive health; actual attempted upstream failures retain existing health semantics.

Audit all fixed-only Session assumptions. In particular, release_opening_payloads currently updates HTTP-only uri/transport/cacertfile/connect_address fields and would fail for a GroupEndpoint struct. Add an explicit group branch that drops opening source, selected configuration and retained group sidecars only when their later consumers no longer need them; retain limits and the independent selection/token identity required for cleanup. Keep the H2 callback submitted URL until bounded response-head extraction, then discard it. managed_path must be H2 from initial admission through cleanup even if checked client/opening source has already been cleared.

## D3. Managed HEAD probes

Options acceptance and live H2 probe support must land together before the first live group prepare GREEN; preparation immediately schedules probes. Pure compilation tests can run earlier.

The group owner chooses the per-member client reservation and charges it before starting a Probe. Probe.init remains network-free. The owner stores token/PID/generation/reservation before claim authorizes open. Keep claim_probe as the admission linearization: authenticate exact PID, token, generation, ready owner, active group, unclaimed state and original deadline. A retired group grants no new claim. A claim won before retirement may already open, but receives cancellation and cannot release accounting before original completion.

Probe validates selected origin, actual protocol and instance, obtains its own request pin and transport checkout under the same health deadline, then builds a fixed H2 HEAD envelope for the exact health target. Use ManagedH2Client for H2 members and HTTPFetchClient for existing H1 members. Do not invent a second Fetch wrapper. HEAD has `body_mode: :none`, no upload, no request trailers, existing finite request limits and the selected member's max_chunk_bytes. Keep exact h2 ALPN, DER trust, no default trust, no TLS/H1 fallback.

Probe stores its selected client, original request and submitted URL. Its poll/event callbacks must use the H2 `{request, submitted_url}` convention until head extraction; H1 uses its existing callback shape. Bind original completion transport-first then group-probe before subscribe/poll delivery. Completion cleanup uses the original request. Confirm completion, finish transport, release request pins, then call probe_finished to refund owner probe bytes/update health. Preserve owner recovery through the same public RequestCompletion; no private client process inspection.

Successful 2xx HEAD is healthy according to existing thresholds; non-2xx or an attempted upstream/protocol failure is failure. Local validation/pin/token/byte capacity rejection remains cancelled/neutral, with no failure/recovery counter mutation. Unexpected HEAD DATA/trailers must follow the fixed bounded protocol contract and be rejected/cancelled rather than silently discarded. Cancellation, deadline, retire, owner death and guardian death preserve completion-held reservations and finite cleanup deadlines. No arbitrary sleeps replace claim/retire or completion barriers.
