## Concrete current path and ownership

1. Native H1 runs `Gaoxy.HTTP.Connection.handle_data` -> parse -> `respond` -> `call_endpoint` -> `module.call(exchange, options)` synchronously in its native connection/socket handling process (`connection.ex:110-152,210-269`). There is no separate H1 request worker at this boundary. The Exchange carries that connection's ThousandIsland socket, admission gate/lease, deadline and input buffer. The existing test ObservedEndpoint (`http_proxy_runtime_test.exs:5-15`) identifies this process with `self()`; it is a reusable observation pattern, not an extra cancellation source.
2. `Gaoxy.Proxy.HTTP` creates a guardian Session but pumps downstream reads and upstream writes in that same native H1 endpoint caller. `read_upload` reads one credited body piece, computes timeout=min(endpoint write timeout, original total remaining), then synchronously invokes `state.client.write_body(state.upload, bytes, timeout)` (`http.ex:750-908`). For managed H1 the selected adapter is `HTTPFetchClient`; its callback directly calls the supported `HTTP.Stream.chunk/3` (`http_fetch_client.ex:208`). A real pending Stream.chunk therefore prevents the caller from executing another pump turn, downstream read or closure poll until the call returns.
3. Downstream closure is detected on `Exchange.read_body_step`/`Socket.recv`, or idle/response-phase `Exchange.poll_connection` -> one-byte `Socket.recv` (`exchange.ex:106-195,205-325`). The upload branch goes directly to `read_upload`; the closure-poll branch does not run concurrently with an outstanding synchronous write. A native socket close/error notification waiting in the process mailbox is not itself evidence of guardian cancellation while the callback is blocked. These inspected files do not install a separate downstream-socket close observer for that phase.
4. The guardian monitors the pump owner, Service, instance and gate (`session.ex:43-52`); it does not directly monitor the downstream socket. Owner death, authenticated Service cleanup cancellation, explicit Session.cancel/expire and its own timers can trigger cleanup (`session.ex:286-341`). The monitored native H1 process can remain alive while blocked, so its process monitor is not a socket-close notification.
5. Guardian cancellation uses the original completion for managed transport ownership, `HTTPFetchClient.cleanup(handle,true)` -> public `HTTP.RequestCompletion.abort_and_await(completion,0)`. Cleanup stays pending until the original completion joins; only then can transport/group/Service ownership finish (`session.ex:1341-1435`, `http_fetch_client.ex:220-221`). The transport owner separately aborts original completion on guardian death using a bounded helper (`upstream_transports.ex:1260-1307`). These are existing cleanup paths, but driving them directly in a test would add a cause other than sole downstream disconnect.

Source establishes a visibility gap at a synchronous call boundary. It does NOT establish how long a real blocked call remains outstanding after downstream close on this host, whether another supported runtime mechanism will terminate the native owner, or that the dependency violates its contract. Existing finite write/total deadlines can terminate the operation independently. Cleanup attributable only to one of those deadlines is deadline coverage, not prompt causal socket-disconnect coverage.
